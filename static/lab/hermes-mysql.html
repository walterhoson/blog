Hermes：给 MySQL 挂一台「分析引擎」

在 MySQL 旁边挂一个单机的列式加速器：分析查询快 2–3 个数量级；数据版本没复制到，就等上几毫秒；一台机器跑赢了用 4 台机器的竞品 PolarDB。

SHEET 01/07问题 · 为什么敢只用一台机器

云上的分析系统大多按「多节点、超大数据」设计。但论文的主张是：多数客户的数据没那么大，多节点反而要反复跨网络搬数据，又贵又慢。现代单机就能装下 TB 级数据。

先猜再看：PublicBI 是一个真实 BI 数据集。你猜里面大多数表有多少行？

答案：大多数表 ≤100 万行，只有少数表超过 1 亿行。Snowflake 公开的真实负载 Snowset 里，大多数查询读的数据不到 1 TB。

多节点到底亏在哪？（论文 §2.2 的账）

分析查询常有多个 join 和 group by。每换一次分组键，就要按新键把数据重新分区（re-partitioning），大表可能在网络里被搬运好几次。

数据倾斜（skew）时更糟：极端情况下 128 核的集群可能只有 1 核在干活。单机可以用 Morsel-driven parallelism 做负载均衡（load-balance），跨机均衡则又要搬数据。

论文的原话：反复 re-partitioning 让系统「既不省成本、也不省电力」。

SHEET 03/07方法 · 三层存储

写入快和分析快互相矛盾。Hermes 的答案是把数据分三层：Row-based Delta（行式 Delta）接写入 → Columnar Delta（列式 Delta）做缓冲 → 压缩列式的 Main store（主存储）给分析，改动逐层下沉。

动手试试为什么需要中间的 Columnar Delta。连点 5 次「发生一次均匀更新」，对比两种设计的写入量示意：

细节：每层为什么长这样

RowGroup 约 16K 行，物理上限 1 GiB。最坏情况下，均匀散布的几行改动会命中几乎所有 RowGroup，一次重写就是把 1 GiB 解压成 2–3 GiB 再压回去，这就是写放大（write amplification）。Columnar Delta 把改动攒久一点，摊薄这笔开销。

Row-based Delta 的更新沿用 Hyper 的 MVCC 版本链：旧版本进 UndoSpace，新事务看不到未提交的改动。

设计假设：表里同时存在的改动不到 10%。靠积极地把改动往下层推来维持这个假设。

SHEET 04/07方法 · Scan = Filter + Append

Scan（扫描）要同时读 Main store 和 Delta。Hermes 不逐行查哈希，而是：先收集 Delta 里改过的行号排好序，扫 Main store 时用 merge 跳过它们（M−D），最后把 Delta 追加到结果末尾。点「下一步」走一遍：

Main store（按行号有序，行 3、7、8 在 Delta 里有改动）
Delta（改动的行 3·7·8 + 新插入的行 13·14）
输出
准备：把 Delta 里的行号 {3, 7, 8} 收集成一个有序集合。
这个 merge 有多便宜？和别人比呢？

两边都按行号有序，merge 时大多在 Main store 上顺序跳过，平摊下来每行不到 1 个 CPU 周期。

对比：Vectorwise 要遍历 Positional Delta Tree（PDT）；ByteHTAP 方案一是对 Main store 每一行做一次主键哈希查找。Hermes 只有整数 merge，没有哈希、没有随机内存访问。

实测：更新比例低于 0.01% 时过滤每行 ≤1 周期；到 1% 时也只涨到 2.5 周期。真正变贵的是 scan Delta 本身。

SHEET 05/07集成 · 和 MySQL 完全对齐

两件难事：看到的数据必须和 MySQL 是同一个 snapshot（快照）（用 GTID→HTID 映射对齐，没复制到就等）；算出来的结果必须和 MySQL 一模一样，包括它的怪脾气。

先猜再看：在 MySQL 里执行 select 3 + 'abc'，结果是什么？

答案：3。MySQL 会把字符串 'abc' 悄悄转成 0。Hermes 让 MySQL 在查询计划里插入「可选类型转换」，把这些隐式规则显式化，保证两边结果一致。

更多对齐手段

另一个例子：substr(123, 1, 1) 返回 '1'，因为整数 123 被转成字符串 '123'。

Replication 端：严格按 commit 顺序复制太慢，Hermes 改为显式跟踪事务依赖，互不依赖的事务可以乱序提交，吞吐更高。

查询要的版本还没复制到？那就等。实测等待是毫秒级，而分析查询本身通常要跑几百毫秒以上，所以几乎无感。

SHEET 06/07证据 · TPC-H 实测

TPC-H SF100（约 100 GiB 未压缩数据）22 条分析查询总耗时：Hermes 15.6 秒，MySQL 8539 秒，4 节点的 PolarDB 29.81 秒。22 条里 Hermes 赢 PolarDB 19 条。

先猜再看：数据放大 10 倍到 SF1000（约 1 TB），你猜 Hermes 的总耗时变成 SF100 的多少倍？

20 倍

答案：约 13 倍（15.6 秒 → 208.4 秒推算）。数据涨 10 倍，耗时只涨 13 倍，而且仍比 4 节点 PolarDB 的总耗时快约 1.9 倍。

例外 Q6：一条纯 scan、纯聚合的查询，PolarDB 更快。原因很物理：4 台机器的内存带宽总和约是单机的 4 倍。查询一复杂（join、group by），多节点要跨网络 re-partitioning，优势就转到 Hermes。

数据来源：PolarDB 的数字来自阿里云官网公布值，不是作者实测，配置是 4 台 32 逻辑核的机器。「PolarDB 折算单机」是作者假设线性扩展、按核数除以 2 得到的推算值推算。

测试机：双路 Intel Xeon 8378A（共 128 线程），512 GB 内存。

SHEET 07/07结论 · 代价与适用边界

天下没有免费的加速器：表里改动越多，scan 越慢。改动 ≤0.2% 时几乎无感，到 1% 时 scan 慢一倍。Hermes 的对策是勤快 merge，把改动压在 1% 以内。Replication 吞吐峰值约每秒 6 万次改动。

其他代价与这篇论文没回答的问题

压缩率约 3 倍：TPC-H 从 115.5 GiB 压到 35.5 GiB，解压几乎免费。这让 TB 级数据能单机驻留内存。

复制吞吐在 8 核后不再涨，受测试机只有 8 个性能核限制；大事务吞吐更低（约 3 倍差距）。

解读论文没展开的部分：数据大于内存时 offload 到 Object Storage 的方案只提了一句，没有评测；对 PolarDB 的对比依赖对方官网数字；单行插入的吞吐受锁竞争限制，作者说会改成无锁操作。

APPENDIX A你答得上来吗

1. Scan 时，Hermes 怎么把 Main store 和 Delta 拼在一起？

Merge 过滤平摊每行不到 1 个 CPU 周期，没有哈希、没有随机访问。

2. TPC-H Q6 上 4 节点 PolarDB 为什么能赢 Hermes？

这是带宽题，不是算法题；查询变复杂、需要跨网络重分区时，优势转到单机。

3. 查询要的数据版本还没复制到 Hermes，会发生什么？

等待几毫秒 vs 查询本身几百毫秒，几乎无感；数据新鲜度因此是最高的。
